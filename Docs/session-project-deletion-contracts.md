## Follow-up acceptance

All routes use /api/v1. POST /sessions/:id/turns now requires {requestId: UUIDv4, prompt: string up to 8000 characters} and returns 202 with {accepted:true,requestId,sessionId,turnId,status,acceptedAt,executionStartedAt,endedAt}. A client generates the ID once before submitting and keeps the exact same ID and prompt after an uncertain response. Repeating a bound request returns that turn's current persisted state, including completed/failed outcomes, without starting another runner. Another prompt or requesting manager with the same ID returns 409. A different ID while the session is active returns 409. Empty/invalid IDs and unknown body fields return 400.

The session row lock serializes competing writers. Acceptance claims the session and writes the QUEUED turn and task status atomically before launch. A unique (sessionId,requestId) constraint backs the binding; historical/internal turns keep null IDs. The persisted execution transition QUEUED to RUNNING is claimed once before calling the runner. Turn/session/task terminal writes form one transaction. HTTP acceptance never asserts successful execution; a nonzero exit, failed runner event or caught spawn error is reflected as FAILED on readback.

GET /sessions/:id/turns/by-request/:requestId returns the same response for a known request. Both submit and readback require sessions.manage and the task's current assigned manager in the current resource workspace. Readback does not require sessions.read, so a manage-only caller can reconcile their own accepted work. Authorization comes from current account/role state; acceptance rechecks OPEN account, workspace, manager and sessions.manage after the HTTP guard. A reassigned manager cannot use another manager's key to retrieve or resubmit their private acceptance. Missing/foreign-scope resources are 404; a different same-workspace manager is 403.

POST /sessions remains 201 and now returns an allowlisted session plus initialTurn. Its first turn is persisted in the creation transaction before asynchronous launch, and current sessions.create is rechecked. Internal Telegram create(start=false) retains a null initialTurn and its existing explicit launch path. Telegram callers now await acceptTelegramTurn using a stable UUIDv4 derived from actor/chat/update identity. It checks current actor/grant/manager/workspace and the persisted chat binding, resets delivery.finished atomically with a newly accepted turn, and never resets or relaunches on a same-key retry. Initial Telegram mode requires sessions.create and a QUEUED session with no accepted turn, preserving create-only authorization; follow-ups require sessions.manage. Both replies include a stable turn ID. The actorless launchTurn/startTurn APIs were removed, and no callers remain. Request UUIDs are normalized to lowercase. GET /sessions/:id returns only documented session/turn fields, excluding embedded task and catalogSnapshot. Turn DTOs include requestId, executionStartedAt and QUEUED. POST /sessions/:id/interrupt now returns documented 200; interrupted:true means signal acceptance by the tracked local process, not descendant-stop proof. These REST responses are no-store.

Unknown acceptance/commit acknowledgement returns 503 with instructions to reconcile or retry the same key. A committed-but-unacknowledged or crashed acceptance can remain QUEUED; an interrupted process can leave RUNNING after restart. A fresh service can read the persisted request and retries still do not launch it again. This implements durable acceptance/readback and at-most-once launch claims, not a persistent execution queue, automatic recovery or prompt replay. Initial session creation has no idempotent request-ID contract; do not describe it as safely retryable after a lost create response.

SESSION01 output replay, SESSION03 durable authoritative state events, and SESSION05 orphan/liveness/recovery remain open. Clients reconcile this increment with REST; existing SSE runner events do not prove a committed terminal state. No new SSE guarantee, process-group containment or SESSION04 preflight was added.

## Project deletion metadata

GET /projects/:id/deletion-requests returns {projectRemoved,requests,audits,limit:100}, the newest 100 of each kind with stable timestamp/ID ordering. This is bounded recent history, not an exhaustive count. GET /projects/:id/deletion-requests/:requestId returns {projectRemoved,request,audit}; a known older ID is independently readable even outside the recent window. After project removal the request is null because its existing cascade deletes it; the durable audit retains requestId and cleanup state. Reads never perform cleanup, create directories, issue tokens or signal runners.

Both routes require projects.delete. Before removal, the current workspace owner or project member can read. Manage-all/read-all do not bypass that relationship. After removal, only the persisted owner or requester within the resource's saved workspace can read. Other former members, unrelated accounts and foreign workspaces do not gain access. Unknown/missing or legacy unscoped removed resources fail closed with 404. Account relocation cannot transplant an old audit into the new workspace. Owning a historical audit does not bypass current authentication/permission requirements.

Request mutation/read responses allowlist IDs, status, request/approval/completion/cancellation timestamps, token expiry/expired/locked indicators, saved WAIT/INTERRUPT choice, a bounded failure code and currently observed tracked session IDs/statuses. tokenSent is true only on the token-delivery mutation response. No token, hash, attempt counter, raw failure, cwd, snapshot, directory or quarantine path is returned. nextAction is OWNER_APPROVAL, RESOLVE_ACTIVE_SESSIONS, CONFIRM_TOKEN, REISSUE_TOKEN, WAIT, NONE or REVIEW_FAILURE; it describes the workflow step, not permission to perform it. Owner-only approval/token confirmation and requester-or-owner cancellation rules remain unchanged. Expired/locked tokens can use the existing owner approval route to reissue. Tracked sessions use the existing workspace/path containment rule, with Windows backslashes handled by Node path checks rather than SQL LIKE; this is not proof all filesystem writers stopped.

Audit responses allowlist id, projectId, requestId, PURGE_PENDING/PURGED/PURGE_FAILED status, sanitized failureCode, nextAction (WAIT/NONE/REVIEW_FAILURE) and timestamps. A recorded purge failure overrides a remaining DELETING request's WAIT guidance with REVIEW_FAILURE; no automatic repair or retry control is invented. Confirmation rereads the audit after its existing awaited purge and returns that recorded status plus projectRemoved instead of always claiming PURGE_PENDING. A quarantine/deletion exception can still return an error; the known request readback exposes the retained audit and whether the project row remains. No automatic purge policy or owner token flow was changed.

PROJECT02's response/readback acceptance is implemented. This does not repair existing deletion concurrency, filesystem/DB boundaries or external-writer containment: those are separate guarantees and FILE03 remains partial.

## Migration and verification

20261011070000_session_acceptance_deletion_scope adds QUEUED to TurnStatus; nullable turn requestId/requestedById/executionStartedAt; a unique session/request index; and nullable ProjectDeletionAudit.workspaceId with a lookup index. It backfills audit scope from the retained department's workspace, never the owner's current workspace. Audits with missing department scope remain null and unreadable after removal until an operator reconciles them from trusted evidence. No existing prompt is replayed or granted new access. PostgreSQL enum additions are additive and are not automatically reversible; coordinate clients for required follow-up IDs/202/QUEUED and writers for the new audit scope/acceptance path. Old binaries bypass these guarantees. Only the isolated localhost:55439/profile_test database was migrated.
