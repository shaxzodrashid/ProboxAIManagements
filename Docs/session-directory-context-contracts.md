## Endpoints and UI behavior

`POST /api/v1/sessions/directory-preflight` takes `{taskId: UUIDv4, projectId?: UUIDv4, cwd?: string, sandbox?: "read-only" | "workspace-write" | "danger-full-access"}`. Sandbox defaults to read-only. Requires current OPEN account, sessions.create, matching task workspace and assigned task manager. Selected projects additionally require current project membership or projects.manage-all, matching project/department workspace and readiness. Public readAccessEnabled and projects.read-all do not grant execution access. No new sandbox privilege is introduced.

Successful HTTP 200 observations return `{project: {id,name,status} | null, requestedPath: string, valid: boolean, normalizedPath: string | null, reason: string | null, guidance, revalidateAtLaunch: true}`. Authorized invalid directories deliberately return valid=false; authorization/identity/DTO failures remain 401/403/404/400. Reasons are ABSOLUTE_PATH_REQUIRED, OUTSIDE_PROJECT, OUTSIDE_ALLOWED_ROOT, POLICY_UNAVAILABLE, SYMLINK_NOT_ALLOWED, NOT_DIRECTORY, NOT_FOUND, ACCESS_DENIED, REAL_PATH_OUTSIDE_SCOPE, DIRECTORY_UNAVAILABLE or PROJECT_NOT_READY. No raw filesystem error or ancestor path is returned. The UI should preserve requestedPath and explain the corresponding corrective action. Normalized path is available only for a valid observation.

Guidance is SELECTED_PROJECT_DIRECTORY or ABSOLUTE_ALLOWED_WORKSPACE_DIRECTORY, not a list of server roots. For a selected project, omitted cwd resolves to that project's department home plus directoryName. A supplied cwd must stay within that selected project. Manual paths preserve existing session-creator/assigned-manager allowed-root scope; this endpoint does not introduce directory browsing or unrelated file metadata. Missing cwd without a project yields ABSOLUTE_PATH_REQUIRED. Paths are bounded to 4096 characters.

`GET /api/v1/sessions/projects/:projectId/execution-context` accepts optional taskId and sandbox query values. Requires sessions.create plus current selected-project membership/administrative scope. It returns the same minimal result plus `capabilities: {canStartSession, requiresAssignedTask}`. Without taskId, context can be inspected but canStartSession=false and requiresAssignedTask=true. With a task, the current manager/workspace checks apply; canStartSession requires valid directory and project readiness. This describes setup capability, not guaranteed provider availability, quota or eventual execution success. Project READY and department ACTIVE are required. No members, department configuration, root listing, credentials, unrelated project or filesystem data is returned.

`POST /api/v1/sessions` accepts optional projectId. cwd is optional only in combination with a selected project; service validation rejects missing manual cwd. Session responses expose nullable projectId. A selected project is retained as selectedProjectId internally and cannot silently turn into a manual session if that project disappears. Telegram's project selection now forwards projectId too.

Creation validates before session/turn/task writes. Invalid directory creation returns 400 `{code:"SESSION_DIRECTORY_INVALID", message, reason, requestedPath, sessionId:null}` and creates no session. The UI keeps the entered path rather than navigating to a successful run. If a valid accepted session subsequently fails launch validation, its already-returned session/turn identities remain valid; GET session and persisted authoritative session.state expose FAILED, NOT_STARTED and DIRECTORY_INVALID (or AUTHORIZATION_LOST). Reconcile that known session rather than falsely showing RUNNING or resubmitting automatically. No extra failure-result endpoint is needed. Detailed per-path launch reason is not added to history.

## Checks and limits

Validation requires an absolute non-NUL path, lexical configured-root containment and selected-project containment before path inspection. It lstat-checks all path ancestors, rejects symbolic links/junctions and non-directories, checks traversal access, resolves the real path and checks containment again. The target must be readable/traversable and also writable when sandbox is not read-only. It never creates directories, probes by writing files or enumerates directory contents. Host fs.access semantics apply; Windows and POSIX permission checks differ, and access observation is not a proof every later runner operation will succeed.

Current task/grant/project/workspace/lifecycle checks and filesystem validation repeat at execution claim and in beforeSpawn. Invalid or revoked accepted work receives an atomic terminal state/event and never reaches child spawn. The real runner performs its own filesystem validation after beforeSpawn as a final guard; failure there is a failed NOT_STARTED run, without raw error disclosure. Existing ownership leases, interruption intent and stale-generation fencing remain in force.

No preflight token or durable directory identity reservation is introduced. External replacement or permission changes can still occur between the last check and spawn, or during execution. Real-path checks do not prove descendant-process or external-writer containment. Existing FILE03 policy remains unresolved. Do not label preflight as eliminating filesystem races.

## Migration and backward compatibility

`20261012000000_session_selected_project/migration.sql` adds nullable TEXT selectedProjectId. No backfill, rewrite or destructive operation; legacy/manual sessions remain null. The selection intentionally has no cascading project foreign key: historical identity survives project deletion and future launch fails closed instead of dropping the scope. Both selected project and department must still resolve in the caller's workspace at launch. Legacy project meaning cannot be inferred from an arbitrary cwd, so no such inference is made.

The migration was applied only to isolated localhost:55439/profile_test. Production rollout requires the schema addition before the new binary. Old clients supplying cwd continue to work after stronger validation; clients may adopt projectId and preflight incrementally. Existing prior-batch turnId and history/SSE rollout requirements still apply.
