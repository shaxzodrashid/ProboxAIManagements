## Contract

POST /projects/:id/files/delete requires a client-generated UUID operationId and path. Retain that ID through retries; never substitute a fresh ID to recover an uncertain request. The durable identity is project-scoped and bound to original requester and normalized path. A completed retry returns the historical stored result before inspecting the live path, so a replacement is untouched. Reuse for another requester/path returns FILE_OPERATION_ID_REUSED. Protected paths return confirmationId plus operationId; confirmation captures content and protection classification in the same tree walk. Changed content/identity requires a new deliberate request. Completed confirmation retries return the stored deletion result.

GET /projects/:id/file-operations returns the latest 100 operations. GET /projects/:id/file-operations/:operationId resolves a known identity. POST /projects/:id/file-operations/:operationId/reconcile inspects evidence and changes database state only; it never moves bytes. All require the existing projects.files.delete permission and existing sensitive project membership/manage-all and workspace checks; no projects.read grant or expanded audience is introduced. Delete and reconciliation require READY; metadata remains available outside READY. Public fields are id, projectId, kind, path, state, result, errorCode, createdAt, updatedAt. Filesystem paths, private keys, source identity and content hashes are excluded.

States: AWAITING_CONFIRMATION, PREPARED, COMPLETED, FAILED, NEEDS_REPAIR. The journal and private trash key commit before movement. Execution and repair serialize on the operation row. File proof includes filesystem root identity and a SHA256 tree layout/content hash; links and special nodes are rejected. Execution checks proof before and after rename, and checks the interactive transaction is still usable immediately before issuing rename. No compensating rename targets the live original path.

A transaction timeout does not cancel filesystem work. Missing private bytes cannot prove an executor stopped. Unmatched PREPARED outcomes remain NEEDS_REPAIR unless durable executor proof establishes no execution can remain active. New operations atomically claim executionStartedAt before any filesystem work and persist executionFinishedAt only after the transaction callback and every issued filesystem await settles. Under the same journal row lock, a tracked operation that never started, or whose finish proof is persisted, can become FAILED/FILE_NOT_MOVED only when its original identity/content match and its private destination is absent. A later executor CAS cannot start a FAILED operation. A finished no-move fence permits a fresh deliberate request, while the old ID remains terminal and never replays. Missing finish proof, crashes, database proof-write failure, mismatched identity and legacy untracked rows remain NEEDS_REPAIR. Matching retained private bytes permit repair to COMPLETED without touching a replacement. AWAITING_CONFIRMATION may fail/expire safely before any execution claim. Overlapping unresolved paths block new operation identities; Windows comparisons fold case, exact source identity blocks aliases/hard links, and Windows trailing-dot/space and alternate-data-stream path aliases are rejected. An unfinished crashed executor still requires a defined independent termination proof before release; merely restarting, waiting or asserting source presence is insufficient.

PREPARED and NEEDS_REPAIR trash records are excluded from the existing expiry cleanup. Uncertain bytes survive expiry until explicit repair. After matching evidence completes the record, ordinary expiry rules apply; repair does not extend retention. COMPLETED is historical deletion success, not a promise that the trash is still restorable.

## Migration and cutover

20261011040000_file_delete_journal adds three trash enum values and an empty ProjectFileOperation table with project-scoped key, state check, unique optional confirmation/trash IDs and project cascade. It does not rewrite legacy trash, confirmations, permissions or accounts. Enum changes are additive; rollback requires deliberate schema handling, not automatic removal. Prisma migration statements are not wrapped in a transaction and a partial DDL failure must be inspected before resuming. No journal can safely be fabricated for legacy uncertain operations. Existing pending confirmations without a journal reject confirmation and require a new deliberate deletion request.

Coordinate migration, writer and client cutover: older clients lack the required operationId and old writers bypass journaling/fences. Mixed versions or raw filesystem/database writers do not inherit these guarantees. Only localhost:55439/profile_test received the migration; production was untouched. All 14 migrations are applied there and Prisma schema diff reports no difference.

## Remaining FILE03 work

Restore still has the preexisting filesystem/database boundary, collision checks and expiry checks; durable restore identity, atomic no-overwrite publication and coordination with expiry need implementation and boundary tests. Strict directory publication through path APIs cannot prove safety when external writers replace ancestor paths; choose a source-grounded native handle-relative primitive or explicit supported external-writer contract before claiming closure. The initial delete rename similarly detects a moved replacement after a path race and retains mismatched bytes for repair; this is detection/retention, not an atomic guarantee that the intended object alone was moved. No filesystem replay, irreversible project purge, new external storage integration or broader access grant is added. Journal retention/terminal pruning and an independent executor-termination proof for crashed NEEDS_REPAIR operations remain future policy/implementation decisions.

## Storage/writer contract blocker

README describes a Linux/systemd VPS deployment; this development laptop is Windows. Existing coding sessions and shell tools may mutate project namespaces independently of database locks. Node does not expose an identity-bound, no-overwrite rename. Windows libuv rename uses MOVEFILE_REPLACE_EXISTING (https://raw.githubusercontent.com/libuv/libuv/v1.x/src/win/fs.c). Windows SetFileInformationByHandle with FileRenameInfo, ReplaceIfExists=false and a relative destination directory handle is a candidate primitive, but needs a reviewed helper, safe ancestor handle opens, explicit supported-volume contract and native race tests (https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info). Linux renameat2(RENAME_NOREPLACE) rejects occupied destinations but still resolves the source leaf by pathname; it cannot atomically compare that leaf with the previously inspected inode (https://raw.githubusercontent.com/torvalds/linux/master/fs/namei.c).

Recommendation: choose and enforce coordination of all project namespace writers, including coding sessions, for the documented Linux deployment, and use native atomic no-overwrite moves with explicit supported-filesystem checks. If independent writers must remain unrestricted, use a managed/isolated storage namespace or explicitly limit strict identity-bound move support to a tested platform/native primitive; do not claim the current Linux path APIs provide the promise. This is a storage/deployment behavior decision, not an approval requirement from a skill. No restore behavior or live writer setting has been silently changed. Restore/expiry fault coverage cannot establish that stronger guarantee before this contract is resolved.

Migration 20261011050000_file_executor_fence adds executionTracked=false and nullable executionStartedAt/executionFinishedAt. It does not backfill proof for legacy rows. Those fields are internal and excluded from HTTP responses. It is additive, only applied to the isolated database, and requires coordinated writer cutover. Three additional real tests verify proof-write failure retains the fence, legacy rows remain fenced and proven finished no-move release allows a new deliberate request.
