# Project Tasks board: frontend implementation handoff

Reviewed against the local backend source on 27 October 2026. This is guidance for the **full project board before AI Session setup**, not a minimal task picker. Paths below have the `/api/v1` prefix; examples are illustrative. Local source does not establish deployment, grants, or production readiness. [Authentication](authentication.md), [Projects](projects.md), and [session handoff](../frontend-session-handoff.md) remain companion guides. Product requirements below do not imply that every supporting API exists.

## Navigation and board

From a project, provide a Tasks tab with project context, board title, search, filters, sort, create, and status management where authorized. Deep-link the project and selected task; opening and closing detail should preserve filters and return focus. Render all configured statuses in board order, including empty columns, using their supplied color/palette and text labels. Default columns are To do, In progress, Review, Done, but IDs are authoritative: names may be duplicated or changed and no label implies completion. Cards should be compact, with title, colored priority badge (including an explicit unset state), deadline, checklist progress, and assignee avatars/names. Fresh assignee identities include nullable `avatar: {assetId,width,height,url}` evaluated using the current AVATAR audience and ACTIVE asset. Fetch the relative URL through the authenticated browser proxy; use initials when null or rejected. Discard cached image bytes on access loss. Never assume an assignment ID has a visible identity.

Load `GET /projects/:projectId/task-board` for columns and `GET /projects/:projectId/tasks/query?scope=all&sort=position` for the full board. Current OPEN project membership is required for human task reads. Board metadata separately requires `tasks.boards.read`, `projects.read` and project read scope; handle either independently denied. The default query remains original-only for compatibility; `scope=all` combines originals and explicit shares, with destination-local status, counts, search and sort. Items include `shared`; shared item `projectId` is the destination and never grants original edit access. Legacy `/shared-tasks` remains available but do not merge it into an already unified page.

Counts describe the entire filtered query generation. Pages are global; a partially loaded column is not empty. Configured empty columns still come from the separately authorized board read. Use `sort=position` for persisted card order (position ascending, creation and ID descending to break legacy ties). Priority/date sorts intentionally override manual order. On narrow screens use horizontally scrollable columns or an accessible column selector; do not truncate actions or trap focus. Provide keyboard move controls with a status menu as well as pointer/touch drag, visible focus, announcements of result/failure, and non-color labels.

## Detail, creation and actions

Open a task detail panel/page with title, description, owner, priority, status, assignees, task deadline, checklist tree, comments and history. Render plain text as text, including comments. Original detail is `GET /projects/:projectId/tasks/:taskId`; shared destination detail is `GET /projects/:projectId/tasks/:taskId/shared-content`, with `/shared-comments` and `/shared-history`. Show current lifecycle and any retained archived/deleted marker; archived projects remain readable but reject new changes. No restore/reopen endpoint is provided for task lifecycle or canonical completion.

Creation is two steps, not an atomic project task creation: `POST /tasks` creates an unlinked execution task; then `POST /projects/:projectId/tasks/:taskId/link` with explicit initial status links it, assigning its owner initially. Persist each request UUID and its exact payload in memory through recovery. Read an uncertain create via `GET /tasks/creations/:requestId`, or retry the same request; never create a new ID to resolve an unknown result. Link uses human revision zero and its own request ID; recover through the human operation endpoint. If create succeeded but link failed, show the created task and offer a safe link retry; do not claim the entire operation rolled back or silently create a duplicate. Title maximum 240, description 16000, optional execution criteria 8000; human detail title is trimmed and nonblank. Creating does not start a session. Set priority, assignments, checklist and deadlines after linking with their separate authorized actions; report partial completion explicitly.

| Action                            | Route suffix under `/projects/:projectId/tasks/:taskId`                           | Authority in addition to current OPEN actor, workspace and project membership                                                                                                     |
| --------------------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Edit title, description, priority | `PATCH /details`                                                                  | Creator/owner and `tasks.details.manage`; priority `URGENT`, `HIGH`, `MEDIUM`, `LOW`, or null to clear. Omit to retain.                                                           |
| Replace assignees                 | `PUT /assignees`                                                                  | Owner and `tasks.assignees.manage`; up to 100 unique IDs. New assignees must be OPEN project members. Reassign/remove checklist items before removing an assignee they reference. |
| Move original card                | `PUT /workflow-status`                                                            | Current task assignee and `tasks.workflow.move`; target must be on this board.                                                                                                    |
| Confirm done                      | `POST /completion/confirm`                                                        | Original-project owner and `tasks.details.manage`. Explicit, one-way canonical confirmation; no reopen.                                                                           |
| Checklist definition              | `POST /checklist`, `PATCH` or `DELETE /checklist/:itemId`, `PUT /checklist/order` | Owner and `tasks.checklists.manage`; section admission applies.                                                                                                                   |
| Check/uncheck item                | `PUT /checklist/:itemId/completion`                                               | `tasks.checklists.complete`, task assignment and that item's individual assignment, original membership and applicable side admission.                                            |
| Comment                           | `POST /comments`                                                                  | Assigned member and `tasks.comments.create`; append-only plain text, maximum 4000 characters.                                                                                     |
| Archive/delete content            | `POST /archive`, `DELETE /content`                                                | Owner and `tasks.details.manage`; one-way retained lifecycle markers, not hard purge.                                                                                             |

The owner is persisted creator, not execution manager, project role or assignee. Only the owner sets priority and confirms canonical done. A move to a Done-named column neither completes the task nor requires confirmation by the API; show an explicit separate confirmation with consequence and no false implication that a move or session result confirmed it. Assignees may move if authorized, including away from a Done column; movement never reopens canonical completion. Disable/hide unavailable actions with explanation, but enforce nothing solely in UI: permissions, membership and assignment can change concurrently. Confirm destructive/one-way archive, delete, unshare and canonical completion in the UI; cancel must cause no request. Status deletion requires an explicit replacement for an occupied column and authority to move every affected task. Board management uses its own revision and `tasks.statuses.manage`; see [board status contract](../task-board-status-contracts.md).

Checklist items have one assignee drawn from the task assignees; maximum 200 items and 200-character titles. Use `checklistSections` tree instead of rendering the compatibility flat `checklist` a second time. Support nesting up to depth eight, section identity and sibling placement; no cross-section transfer, and a parent with children cannot be deleted. Destination-section edits require original owner authority plus admission to that side. Retained inactive sections remain visible where authorized. See [shared checklist contract](../shared-checklist-tree-contracts.md) for ordering and lifecycle details. Completion attribution survives reassignment; checking and unchecking update attribution according to backend state.

## Search, paging and dates

The query accepts `scope=original|all` (default original), trimmed literal case-insensitive `q` (1–200), `priorities`, `statusIds`, `assigneeId`, `sort`, `limit` (1–100, default 50), and opaque `cursor`. Sort supports `position`, `priority`, `deadlineDate`, `deadline`, `createdAt`, each optionally prefixed `-`, up to three distinct fields. Default `-priority,-createdAt`; unset priority/deadline sorts last. `deadline` sorts timed values first by pinned instant, then date-only by calendar date, unset last; direction applies within buckets. `deadlineDate` compares calendar dates only. With `scope=all`, filters/counts apply to both original and shared entries using local status IDs. Debounce search, reset cursor on any filter/sort change, and distinguish no matches from an empty project. If continuation returns `409 HUMAN_TASK_QUERY_CHANGED`, discard all pages and reload page one; never combine generations. Refine filters on `503 HUMAN_TASK_QUERY_SCOPE_LIMIT`.

Task deadline is a separate `/tasks/:taskId/deadline` resource with its own revision and `tasks.deadlines.manage`; linked tasks additionally require owner and current project membership. Read its edit snapshot before writing; do not use the human revision. Checklist deadlines use the checklist mutation and human revision. Date-only values are calendar dates, never UTC midnight. Timed values require local `date`, `time` (HH:mm), IANA `timeZone`, and matching explicit `utcOffset`; reject nonexistent times and ask the user to choose the offset in repeated DST hours. Display the supplied local date/time and zone, optionally a viewer-local equivalent; do not silently reinterpret. Null clears. Deadlines do not schedule notifications. See [deadline contract](../task-deadline-contracts.md) and [checklist deadlines](../checklist-item-deadline-contracts.md).

## Examples and recovery

All IDs below are illustrative UUIDv4 values. Direct API uses bearer auth; a browser session cookie does not authenticate these original routes. The local `/browser/api` allowlist now includes the task board routes described here; local end-to-end verification covers authentication, CSRF, revisions, recovery, query forwarding, deadlines and SSE. Deployment availability remains separate. The proxy retains session and CSRF checks and the upstream routes still enforce their own authorization. Do not put bearer tokens in browser storage. See [authentication](authentication.md).

```http
GET /api/v1/projects/11111111-1111-4111-8111-111111111111/tasks/query?scope=all&sort=position&priorities=HIGH,URGENT&limit=50
Authorization: Bearer <access-token>
```

The response is `{ "generation": "<opaque digest>", "items": [...], "total": 0, "priorityCounts": [...], "statusCounts": [...], "hasMore": false, "nextCursor": null, "asOf": "2026-10-27T12:00:00.000Z" }`; counts are filtered and include all priority bands, even zero. Each fresh item includes `id`, `projectId`, `title`, `description`, `ownerId`, `statusId`, `workflowStatus`, nullable `priority`, `deadline` and canonical `completed`, persisted local `position`, query `shared` discriminator, `revision`, `assigneeIds`, `assigneeIdentities`, `checklist`, `checklistSections`, `lifecycle`, project archive and timestamps. Consult [query contract](../human-task-query-bio-evidence.md) and current DTO for full projection; historical receipts can lack later-added fields.

```http
POST /api/v1/tasks
Authorization: Bearer <access-token>
Content-Type: application/json

{"requestId":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa","title":"Prepare release","description":"Review the release plan"}
```

On 201, use the returned task `id`; the response also includes workspace, title, description, criteria, runner status, creator, manager and timestamps. Then link using a different request ID and the returned ID:

```http
POST /api/v1/projects/11111111-1111-4111-8111-111111111111/tasks/22222222-2222-4222-8222-222222222222/link
Authorization: Bearer <access-token>
Content-Type: application/json
If-Match: "0"

{"requestId":"bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb","statusId":"33333333-3333-4333-8333-333333333333"}
```

A successful human mutation returns `{taskId, requestId, actorId, action, revision, before, after, comment, createdAt}`; `after` is a frozen human snapshot, not a fresh identity projection. For subsequent edits use the current human revision:

```http
PATCH /api/v1/projects/11111111-1111-4111-8111-111111111111/tasks/22222222-2222-4222-8222-222222222222/details
Authorization: Bearer <access-token>
Content-Type: application/json
If-Match: "1"

{"requestId":"cccccccc-cccc-4ccc-8ccc-cccccccccccc","priority":"HIGH"}
```

A move uses `PUT .../workflow-status` with the same headers and body `{ "requestId": "<UUIDv4>", "statusId": "<same-board UUIDv4>" }`. For manual placement add `beforeTaskId: "<card UUID>"` to an original or shared move, or null to append. The neighbor must currently be in that destination column, may be original or shared, and cannot be the moved card. A missing/moved neighbor returns `409 TASK_CARD_ORDER_CHANGED`. Omission retains same-column order and appends when changing column. Placement changes the moved task revision and uses the same request recovery; numeric labels of neighbors may shift without changing their human revisions. Concurrent moves serialize under the workspace lock; each request applies against its current neighbor position. A stale task revision still returns 409. Confirmation uses `POST .../completion/confirm` with `{ "requestId": "<UUIDv4>" }`; shared state reads return `taskId`, `projectId`, `statusId`, `revision`, nullable `completed`, and `lifecycle`. `completed: null` means no recorded confirmation, not an inferred false from the column. Fresh original, unified and shared task reads expose this canonical field; frozen human mutation receipts retain their existing snapshot projection. Checklist checks and card moves never confirm the task.

For each mutation preserve request ID, original quoted `If-Match`, and exact payload. A matching authorized retry returns the saved outcome; changed reuse or stale revision is 409. Missing revision is 428; malformed input is 400. For an uncertain timeout/500/503, read the applicable `/operations/:requestId` or retry the identical request; a 404 while in flight does not prove failure. Never issue a new ID or blindly replay a stale draft. Re-fetch fresh state after success, conflict or authorization changes. Optimistic movement should show pending, prevent concurrent edits on that task, and roll back or reconcile on rejection; never assert rollback on an unknown outcome. Surface 401 sign-in, 403 missing permission, 404 missing/inaccessible, validation errors, conflict and unavailable states without disclosing inaccessible resources. Keep draft text where safe.

## Shared tasks and sessions

An owner can explicitly share an original task to another same-workspace project where they are a current member using `PUT .../shares/:targetProjectId` and explicit destination `statusId`; `DELETE` removes that association only. Both require `tasks.create`, original ownership and current membership on both sides. Destination workflow is local: an assigned destination member with `tasks.workflow.move` uses `PUT .../shared-workflow-status`; it does not move the original board or confirm completion. Canonical fields, checklist sections, comments, history and completion are shared subject to current membership; destination access does not grant original edit authority or expose other project identities. Sharing and local movement use the common human revision and `/sharing-operations/:requestId` recovery. See [shared content](../shared-task-content-contracts.md) and [shared association](../shared-human-task-contracts.md).

The board is the first deliverable and remains useful without an AI session. A later session launch may use an existing task identity only after checking the separate session permissions and project execution context; human assignment is not execution manager authority. A board card, status, completion or successful runner does not itself create a session or grant transcript/action access. Follow the [session handoff](../frontend-session-handoff.md) for exact preflight, creation and recovery; do not invent an all-in-one launch endpoint.

Subscribe to `GET /projects/:projectId/tasks/events/stream` (browser proxy supported). SSE `board.invalidated` carries only `{generation}`, an opaque caller-bound token; `board.heartbeat` has empty data. The initial invalidation always requires a fresh REST query. Persisted committed state is checked every second; changes may coalesce. This is an invalidation feed, with no audit replay, task payload or per-change delivery guarantee. On invalidation, discard cached pages and requery current filters; on reconnect, authorization failure or stream close, reconcile through REST. Each batch checks OPEN membership, account/session revocation and token expiry. Unshare removes content from the next authorized snapshot. Profile display metadata is fresh on reads but is not a task mutation event. Keep focus/manual refresh for profile changes and transport outages. Load and proxy capacity should be checked before broad rollout; every active stream polls the persisted board generation.

## Frontend acceptance matrix

| Scenario                               | Expected behavior                                                                                                                                                 |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Member opens a board                   | Ordered configured statuses including empty ones; cards from unified paging; correct scope and no false total.                                                    |
| Missing board permission or membership | Explain unavailable portion; do not infer columns or leak task details.                                                                                           |
| Search, filter, sort and pagination    | Unified scope explicitly requested; filters reset cursor; counts use local status; generation conflict replaces pages.                                            |
| Create then link                       | Recover each uncertain step with its original request; partial create/link failure is explicit; no duplicate task or automatic session.                           |
| Owner edits and assigns                | Validate limits, priority and member eligibility; checklist handoff prevents invalid removal; refresh authoritative revision.                                     |
| Assignee moves card                    | Pointer, touch and keyboard equivalent; pending announcement and rollback/reconciliation; no completion inferred. Unauthorized and stale attempts cannot persist. |
| Owner confirms completion              | Explicit irreversible confirmation; result is canonical across shares and independent of local column; no fabricated reopen.                                      |
| Checklist and deadlines                | Nested sections, item ownership, child deletion constraint and completion attribution work; date-only and DST ambiguity remain accurate.                          |
| Shared task                            | Destination local move only; canonical data visible with authorized membership; unshare revokes access on next read and retains source.                           |
| Archived/deleted or revoked            | Read retained state where authorized; reject new writes, recover saved operations under fresh authority, preserve safe draft and update UI.                       |
| Network failure                        | Loading skeletons, retryable errors, empty/no-results distinction and no duplicate writes; unknown outcome reconciled before retry.                               |
| Mobile and accessibility               | Responsive column navigation, semantic labels, focus restoration, keyboard actions, screen-reader status and non-color priority/status cues.                      |
| Session launch                         | Board functions without sessions; optional launch checks separate execution authority and uses session contract.                                                  |
