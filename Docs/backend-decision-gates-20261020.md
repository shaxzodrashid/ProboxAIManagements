# Remaining decision gates — 20 October 2026

These are specific gates for the next feature slices, not a claim that the entire
backend is blocked or that every existing implementation has been exhaustively
audited. Independently confirmed correctness defects can still be fixed. The
current recovery/read-availability and project mutation authority corrections
proceeded without waiting for these choices. No recommendation below is approval.

1. **Ordinary group-message sending — settled20 October.** Admitted OPEN members
   send by default; owner restrictions are explicit. No extra owner grant is
   required for normal participation. The local text-send slice is documented in
   `group-text-sending-contracts.md`; this is no longer an unanswered question.
   This does not reopen settled owner-granted invitation rights, inviter-selected
   initial history, DIRECT/APPROVABLE admission or REST/Telegram preferences.
2. **Detailed session tool disclosure.** May current assigned session managers
   retrieve selected best-effort redacted commands/output, and which fields and
   bounds are allowed? Recommendation: require an explicit versioned allowlist
   under existing session permission/resource scope, with omission/truncation
   markers; keep STRICT_METADATA until selected. Retention approval alone does
   not authorize public raw archives, hidden reasoning or arbitrary tool results.
3. **FILE03 — authorized engineering, not another product question.** The parent
   clarified20 October that internal restore/expiry coordination, filesystem
   locking and native no-overwrite mechanics are within recoverable-deletion
   authorization. Diagnose/implement supported internal guarantees and explicit
   busy/unknown outcomes where safety cannot be established. Do not claim exclusion
   of uncontrolled external writers or alter live runner/storage/security settings.
   Current path checks cannot prove OS containment. No blanket new authority is
   requested; this is concrete implementation and verification work.
4. **SPACE01–04 article authority/content contract.** Which project actors may
   read/create/edit/publish/restore articles, and what block/version/media rules
   apply? Recommendation: explicit project-scoped capability plus current
   membership, deliberate publish/version actions, portable validated blocks and
   private media; no automatic workspace-admin/public publishing. Multiple roots
   and Previous/Next reading order are selected; those do not select disclosure
   or an editor/storage integration.
5. **Broader task collaboration and typed inclusion.** What source edit/delete/
   reopening effects should propagate to shared destinations? Which task/file/
   article identities may be included and resolved for each viewer? Recommendation:
   preserve canonical audit and current per-viewer authorization, use explicit
   revisioned operations, and never substitute current file bytes for historical
   evidence. Existing canonical shared reads are approved and implemented;
   per-side progress/comments/history isolation remains exploratory.
6. **Optional account identity/recovery changes — excluded.** Username/phone edits,
   verification, Telegram-binding and new session-revocation flows remain outside
   the current profile editing scope. They are not prerequisites or pending
   questions for the authorized work.

7. **Ambiguous started-session recovery — safety constraint.** Preserve uncertain
   execution fences and never automatically replay. Trusted proof that execution
   and descendants stopped is required before release; an accepted interrupt alone
   is insufficient. No manager resume-anyway policy is introduced. Never-started
   recovery is already implemented. This is not an additional question to the user.

Internal restore/expiry coordination, stable identity validation, article forest
ordering/cycle checks, DTO/OpenAPI work and source-grounded regression fixes are
engineering choices within authorization. Only items2,4 and5 are pending product
decisions currently surfaced by the parent. They do not block all work
on FILE03, articles, shared tasks or profiles. Optional username/phone edits are
unselected scope, not prerequisites to the existing profile feature.

Agents remain explicitly deferred. Frontend intent/recovery wiring and production
TLS/keys/storage/migration/security operations are separate scope, not backend
product questions to silently resolve. Postman actions, retries and approval
requests remain stopped. No group-policy reminder is issued by this inventory.
